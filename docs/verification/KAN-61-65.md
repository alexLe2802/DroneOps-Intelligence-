# KAN-61 / KAN-65 — UAV proposals and review

2026-11-14 · Qthong · baseline `65633b3` + working tree. Implementation evidence only; not deployment or acceptance.

## Result

- Operator edits create a separate `UavReviewRequest`, containing the current/proposed registry snapshots, submitter/time and base version. One Pending request per UAV. Current approved specs and operational status remain intact.
- Manager compares fields and submits exact `requestId`, `expectedVersion` and a required decision reason. Approval applies the selected proposal and saves the decision atomically. Rejection preserves approved current information. Initial registration becomes Active only after approval; rejection becomes Rejected and supports corrected resubmission.
- UAV and review status concurrency tokens, serializable transaction, UAV row lock and unique Pending index prevent duplicate/stale decisions. Codes are unique without case distinctions. Bound Code/manufacturer/model/serial changes require verified FC replacement.
- Active execution, active flight mission or fresh armed FC evidence blocks registry changes and deactivation. Old armed samples are not presented as fresh. Ownership never changes.
- Mission approval and dispatch/preparation check Active UAV, owning active Operator, current approved license covering the full flight window, overlapping allocations and other active executions. Transactional paths lock UAV then User then Pilot; User/Pilot order matches account workflows. UAV approval clears old mission preparation consent, requiring new preflight/confirmation.
- Both roles see proposal and review/status history. Operator has no Manager actions. UI blocks stale retries until reload; no polling added. Concurrent image writes also advance the UAV version and reject stale writes. Existing image moderation remains an independent optional-media policy and never implies UAV approval. Decision notifications are sent only after commit.
- Legacy Pending records can be reviewed from their displayed current record. Historical submitter/time remain null, not reconstructed. Existing Active/Inactive records are retained as the current approved baseline; overwritten historical specs cannot be recovered by this migration.
- Manager Operator allocation drill-down remains the KAN-28 implementation. Review decisions prevent physical UAV deletion to retain audit; unbound registrations without decisions may still be removed.

## API

- `GET /api/uavs/{id}/reviews`: Manager fleet scope / Operator own UAV only. Returns current, pending and immutable captured history; legacy missing evidence explicit.
- `PUT /api/uavs/{id}`: existing spec DTO + required observed `expectedVersion` (missing/stale rejected).
- `PUT /api/admin/uavs/{id}/{approve|reject|activate|deactivate}`: `{ expectedVersion, requestId, reason }`. Approve/reject require exact pending request identity; explicit legacy registration uses null requestId. Status actions require null requestId. Missing version, wrong request, concurrent mutation and active-flight blocks return conflict. Manager cannot approve own submission.
- Next proxy allowlist includes only GET reviews; existing origin/JWT/role checks remain. Image rejection POST is explicitly forwarded.
