27 [p] II. Testing Documentation
28 [p] 1. Scope of Testing
29 [p] Testing covers authentication and role scope, user media, mission planning and review, waypoint and segment validation, telemetry ingestion and monitoring, incident handling, post-flight reports and advisory AI. Low-level flight-control algorithms and aviation certification are outside the software test scope.
30 [p] Unit tests exercise business rules and processing functions with deterministic inputs. Integration tests cover API, persistence, scope and provider boundaries. System tests cover the two-role mainflows and recovery scenarios. Flow owners prepare tests; another team member reviews the cases and evidence.
31 [p] Tests use a disposable database, scoped test accounts, configured route and restriction fixtures, timestamped telemetry replay, and provider/email stubs. Live MAVLink, provider and email behavior require separate integration evidence. The case designs are prepared; no execution results are recorded in this document.
32 [p] 2. Test Strategy
33 [p] The strategy combines functional and boundary tests, authorization checks, transaction and recovery tests, realtime measurements and usability checks. Each test is linked to its function, controlled inputs, expected result and execution evidence.
34 [p] 2.1 Testing Types
35 [p] Functional tests use normal, invalid and boundary inputs to verify required outcomes. Authorization tests use distinct Operators and a Manager to verify role and record scope. Reliability tests use duplicate/out-of-order samples, database failure, missing packets and provider errors. Performance tests record latency, loss and workload conditions. Usability tests cover visible feedback, keyboard navigation and desktop/narrow-screen layouts. A case passes only when its expected outcome and evidence agree.
36 [p] 2.2 Test Levels
37 [p] Unit: deterministic rule, transaction, aggregation and response-processing checks owned by the function author and peer reviewer. Integration: disposable-database/API and provider-stub scenarios owned by the flow owner. System: a tagged Web/API build and controlled telemetry source exercised by the team. Acceptance: nominated mainflows reviewed against agreed requirements with supervisors. The matrix below shows the applicable testing levels.
